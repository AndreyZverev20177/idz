# Ревью соответствия ТЗ: Music Analytics

**Объект:** исходный архив `idz.zip` от 22.11.2026 и доработанная версия.
**Метод:** последовательные проверки с пяти профессиональных позиций: системный
архитектор, разработчик Python/API, QA, DevOps и специалист по UX/безопасности.
Это ролевое ревью одного помощника, а не заключения пяти независимо запущенных
внешних агентов.

## Краткий результат

Исходник можно было запустить как Streamlit-приложение в подходящем окружении;
основные расчёты были выделены в `music_analysis.py`, а шесть тестов проходили.
При этом ТЗ **не выполнялось полностью**: пустой README, отсутствие API,
Dockerfile, структуры `main/utils/data/tests` и Git-истории в архиве.

Доработанная версия исправляет основные функциональные и структурные недостатки:
**23 теста прошли**, JSON-контракт FastAPI проверен на реальных запросах через
TestClient. Запуск Docker и настоящего Streamlit-сервера в рабочем окружении
проверить не удалось: Docker и Streamlit здесь не установлены, а скачать пакеты
из сети нельзя. Аналогично не запущены `black` и `flake8`: конфигурация и CI
подготовлены, но выполнение форматтеров надо подтвердить при запуске workflow.

| Пункт ТЗ | Исходный архив | После доработки |

| Понятный Streamlit-интерфейс | Есть | Доработан, но UI-сервер не проверен в браузере |
| Python, функции, классы, модули | Функции есть; классов и пакетов нет | Функции, пакет `utils`, dataclass, модели Pydantic |

## Замечания по ролям

### 1. Системный архитектор

- **Критично:** API отсутствовал, хотя требовался. Добавлена точка входа `main.py`
  с маршрутом `POST /api/v1/analyze`, схемами `Track`, `Artist`, `Genre`,
  `AnalysisResponse` и `GET /health`.
- **Высокий приоритет:** логика проверки CSV находилась непосредственно в
  Streamlit-сценарии, поэтому её невозможно было независимо переиспользовать.
  Создан `utils/data_loader.py`, общая аналитика выделена в `utils/analysis.py`.
- Выбрана минимальная архитектура без БД, брокера сообщений и обязательного
  запуска двух сервисов. Streamlit и HTTP API используют одну бизнес-логику.
- В ТЗ Telegram-бот указан как идея архитектуры, но Streamlit задан как
  обязательная демонстрация. Telegram-бот намеренно не добавлен.

### 2. Разработчик Python / API

- **Функциональный дефект:** порог прослушиваний в таблице задавался пользователем,
  а график строился с жёстко заданным порогом. Исправлено передачей `threshold`.
- **Логическая неточность:** `get_popular_tracks` применял строгое `>` к
  «минимальному количеству». Теперь используется `>=`.
- `read_csv` мог завершиться ошибкой на плохом CSV; теперь ошибки сообщаются
  пользователю, поддерживаются UTF-8 и CP1251, применяется лимит 10 МБ.
- В первоначальном `requirements.txt` были зафиксированы десятки транзитивных
  пакетов. Теперь перечислены только основные зависимости; тестовые инструменты
  вынесены в `requirements-dev.txt`.

### 3. QA

- Исходно было 6 тестов, не проверяющих API, кодировки, пустые CSV, пропущенные
  столбцы и отрицательные/текстовые значения прослушиваний.
- Добавлены тесты фильтрации, парсинга исполнителей без выполнения кода,
  диаграммы с правильным порогом, валидации CSV и ошибок API.
- **Фактическая проверка:** `python -m pytest -q` -> `23 passed`.
- **Фактическая проверка:** `python -m compileall -q ...` -> успешно.
- **Ограничение:** реальное взаимодействие в браузере и поведение контейнера
  не протестированы.

### 4. DevOps

- Добавлены `Dockerfile`, `.dockerignore`, `.gitignore`, GitHub Actions workflow.
- Описаны отдельные команды контейнерного запуска Streamlit и API.
- Создано локальное Git-историческое представление двух изменений для переноса.
- **Блокер:** у подключённой GitHub-учётной записи нет доступного репозитория
  `AndreyZverev20177/idz`; доступный инструмент GitHub не умеет создавать новые
  репозитории. Произвольные существующие репозитории не менялись.
- **Риск:** Dockerfile не прошёл фактическую `docker build`, форматтеры не
  выполнились из-за ограничений среды. Их нужно проверить на GitHub Actions.

### 5. UX и безопасность

- В интерфейсе добавлены подсказки о структуре CSV и диагностике выброшенных
  записей. Исключена рассинхронизация таблицы и графика.
- API ограничивает размер файла, тип входного файла и диапазоны параметров.
- При обработке списка исполнителей используется `ast.literal_eval`, а не `eval`.
- В архиве исходника не обнаружено явных секретов (`.env`, токенов и ключей).
- В итоговый архив не включены `__pycache__` и `.pytest_cache`.
- Вывод «прослушивания исполнителей» не является уникальным числом прослушиваний
  по всей библиотеке: совместные записи засчитываются каждому исполнителю.

## Что необходимо сделать для полной сдачи

1. Запустить `docker build -t music-analytics .` и контейнер Streamlit.
2. Посмотреть интерфейс в браузере на демонстрационном CSV.
3. Запустить `black --check` и `flake8` (либо дождаться проверки GitHub Actions)
   и внести требуемые форматирующие исправления.
4. Создать отдельный репозиторий GitHub, например приватный `idz`, и загрузить
   Git-историю из переданного bundle. Убедиться, что workflow прошёл зелёным.

**Итог:** исправленная версия значительно ближе к ТЗ и проходит 23 доступных
автоматических теста, но подтверждать «100% соответствие» до Docker/UI/CI и
публикации в GitHub было бы некорректно.
